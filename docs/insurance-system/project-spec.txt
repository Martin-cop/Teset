مشخصات پروژه: سامانه مدیریت لیست حق بیمه کارگزاری رسمی سازمان تامین اجتماعی
تاریخ تهیه: 1405/8/18
این سند جمع‌بندی نهایی تصمیم‌های طراحی است و باید مبنای تولید کد باشد.

==================================================
1. شرح کار فعلی کارگزاری
==================================================
- کارگزاری لیست حق بیمه کارکنان کارفرمایان را از طریق سایت سازمان تامین اجتماعی ارسال می‌کند.
- هر ماه از کارفرما (یا رابط کارگاه) از طریق واتساپ، پیام‌رسان‌های داخلی (بله، سروش، ایتا) یا پیامک تغییرات پرسنل پرسیده می‌شود. مثال: «مرضیه رضایی از 5/2/1405 ترک کار کرده است».
- کارمند با نام کاربری و رمز کارفرما وارد سایت تامین می‌شود، لیست را تنظیم و ارسال می‌کند.
- حق بیمه با کارت بانکی کارفرما و رمز پویایی که کارفرما می‌فرستد، به‌صورت اینترنتی پرداخت می‌شود. رسید یا اسکرین‌شات برای کارفرما فرستاده می‌شود.
- حق‌الزحمه کارگزاری طبق فرمول محاسبه و به کارفرما اعلام می‌شود. کارفرما مبلغ را کارت‌به‌کارت به حساب مدیر کارگزاری واریز و رسید را می‌فرستد.
- اکنون همه چیز در یک فایل اکسل نگهداری می‌شود. کاربران روی ویندوز 10 و 11 کار می‌کنند.
- اینترنت بین‌الملل ایران ممکن است قطع شود. شبکه داخلی، سایت تامین و درگاه‌های بانکی در قطعی کار می‌کنند.

==================================================
2. هدف فاز 1
==================================================
کنار گذاشتن کامل فایل اکسل. برنامه باید همه نیازهایی را که اکسل برآورده می‌کرد پوشش دهد.

قاعده مهم: محدودیت‌های اکسل نباید در طراحی تکرار شوند:
- کد یک‌حرفی ممنوع است. به‌جای «ح»، «غ» و «خ» از مقادیر کامل استفاده شود: «حضوری»، «غیرحضوری»، «پرداخت توسط کارفرما»، «پرداخت توسط کارگزاری».
- ستون تکراری برای هر ماه ممنوع است. هر ماه یک ردیف جدا با سال و ماه کامل دارد.
- ستون بی‌معنا (Column1 و مانند آن) ممنوع است.
- شیت جدا برای کارگاه‌های غیرفعال لازم نیست. کارگاه وضعیت «غیرفعال» با تاریخ می‌گیرد.
- نام پرسنل دستی تایپ نمی‌شود. کاربری که کار را انجام داده خودکار ثبت می‌شود.
- مقادیر تکراری مثل وضعیت و نحوه ارسال از فهرست انتخاب می‌شوند.

==================================================
3. معماری
==================================================
- وب‌اپلیکیشن یکپارچه ماژولار (Modular Monolith). میکروسرویس استفاده نشود.
- معماری API-first و لایه‌ای: رابط کاربری، API، منطق کسب‌وکار، داده و اتصال‌ها.
- هیچ منطق کسب‌وکاری در رابط کاربری نوشته نمی‌شود. همه رابط‌ها (وب، ویندوز، اندروید، اپ کارفرما) فقط از API استفاده می‌کنند.
- دو API جدا: API داخلی برای کارکنان، و API بیرونی برای کارفرما در فاز 2. گاوصندوق هرگز از API بیرونی در دسترس نیست.
- نسخه ویندوز همان نسخه وب است که به‌صورت PWA نصب می‌شود.

==================================================
4. فناوری
==================================================
- بک‌اند و API: C# با ASP.NET Core (آخرین نسخه LTS)
- رابط وب: React با TypeScript
- پایگاه داده: PostgreSQL
- مرورگر اختصاصی (فاز بعد): C# با WebView2 (نه Electron)
- اپ موبایل (فاز 2): React Native با TypeScript
- احراز هویت: OpenID Connect
- اجرا: Docker
- کنترل کد و CI: GitHub و GitHub Actions
- تست: تست خودکار منطق مالی، تست کامل مرورگر با Playwright
- نسخه نمایشی رزومه (با داده ساختگی): Azure

==================================================
5. محیط اجرا
==================================================
- فاز 1: سرور داخل دفتر، سیستم‌عامل Ubuntu Server LTS، همه بخش‌ها داخل Docker. فقط شبکه داخلی و HTTPS داخلی.
- کلاینت‌ها: ویندوز 10 و 11 با Edge یا Chrome.
- پشتیبان: هر شب خودکار و رمزنگاری‌شده روی دیسک جدا، به‌اضافه یک نسخه بیرون از دفتر، و آزمایش ماهانه بازگردانی.
- فاز 2: همان مجموعه روی سرور ابری داخل ایران برای دسترسی کارفرما. گاوصندوق در دفتر می‌ماند.
- محیط آزمایش جدا با داده ساختگی، هرگز با داده واقعی.

==================================================
6. زیرسیستم‌های فاز 1
==================================================
1. امنیت و دسترسی
   - کاربر = یک شخص از جدول اشخاص، با کد کاربری.
   - نقش‌ها و مجوزهای جزئی، مثل «دیدن CVV2» و «تأیید واریز».
   - محدوده دسترسی: هر کاربر فقط کارگاه‌های سپرده‌شده به خودش یا همه را می‌بیند.
   - ورود دومرحله‌ای (رمز + کد پیامکی). قفل حساب پس از چند تلاش ناموفق. خروج خودکار.
   - بازیابی رمز فقط روی موبایلی که سامانه شاهکار تطبیق آن را با کد ملی خود کاربر تأیید کرده است (از طریق شرکت واسط مجاز). اگر سیم‌کارت به نام شخص نیست، فقط با تأیید مدیر و ثبت در لاگ.
   - کاربر حذف نمی‌شود، فقط غیرفعال می‌شود.
   - مدیریت کلید رمزنگاری و تعویض دوره‌ای آن.
   - ورود فقط از دستگاه‌ها یا شبکه مجاز دفتر.
   - سیاست‌های امنیتی قابل تنظیم: قوانین رمز، مدت نشست، سقف نمایش اطلاعات حساس.
   - پایش رفتار مشکوک و هشدار پیامکی به مدیر.

2. لاگ و ممیزی
   - ثبت تغییر داده: کاربر، زمان، دستگاه یا IP، رکورد، مقدار قبل و بعد.
   - ثبت مشاهده اطلاعات حساس، همراه دلیل.
   - ثبت رویدادهای امنیتی: ورود، ورود ناموفق، بازیابی رمز، تغییر دسترسی.
   - ثبت عملیات: چاپ، خروجی اکسل.
   - پایگاه داده جدا، فقط افزودنی. برنامه حق ویرایش یا حذف لاگ را ندارد.
   - زنجیره هش: هر ردیف هش ردیف قبل را دارد.
   - کپی دوره‌ای بیرون از سرور.
   - گزارش لاگ بر اساس کاربر، بازه زمانی، رکورد و نوع عمل.

3. اشخاص و مخاطبین
   - هر شخص حقیقی یا حقوقی فقط یک بار ثبت می‌شود. کارفرما، رابط، بیمه‌شده و کاربر نقش‌های یک شخص‌اند.
   - شناسه: کد ملی، شناسه ملی شرکت، یا کد فراگیر اتباع.
   - شماره‌های تماس نامحدود، متصل به شخص یا کارگاه. نوع قابل انتخاب (موبایل شخصی، موبایل کارگاه، تلفن ثابت و غیره)، علامت «اصلی» و «فعال»، تأیید شاهکار، پیام‌رسان‌های فعال روی شماره.
   - آدرس‌ها و یادداشت‌های نامحدود.

4. کارگاه
   - کد کارگاه، نام، شعبه تامین، نوع فعالیت.
   - وضعیت از فهرست (فعال، غیرفعال، جدید و غیره) با تاریخ.
   - گروه کارگاه: فیلد اختیاری از جدول «گروه کارگاه».
   - کارفرمایان نامحدود با تاریخ شروع و پایان. یکی اصلی و فعال است. قید پایگاه داده اجازه دو کارفرمای اصلی فعال را نمی‌دهد. کارفرمای حقوقی مدیرعامل و صاحبان امضا دارد.
   - رابط‌های نامحدود با نقش (رابط، حسابدار، نماینده)، تاریخ و راه تماس ترجیحی. رابط از کارفرما جداست.
   - ردیف‌های پیمان.
   - کارمند مسئول کارگزاری.
   - نام کاربری و رمز سامانه تامین در گاوصندوق، با تاریخچه.

5. بیمه‌شدگان
   - پرونده هر بیمه‌شده مستقل از کارگاه. با کد ملی شناخته می‌شود، پس جابه‌جایی بین کارگاه‌ها خودکار دیده می‌شود.
   - سوابق اشتغال: کارگاه، تاریخ شروع کار، تاریخ ترک کار، شغل.
   - ردیف ماهانه لیست: روزهای کارکرد، دستمزد، حق بیمه.
   - گزارش جامع همه لیست‌ها و پرداخت‌های هر نفر در همه کارگاه‌ها.

6. لیست حق بیمه (هسته سیستم)
   - هر لیست: کارگاه، سال، ماه، ردیف پیمان، نوع (اصلی یا اصلاحی)، تعداد بیمه‌شده، مبلغ حق بیمه، شماره پیگیری سامانه.
   - نحوه ارسال: «حضوری» یا «غیرحضوری»، پیش‌فرض «غیرحضوری»، و ثبت مراجعه‌کننده در حالت حضوری.
   - پرداخت حق بیمه: «توسط کارفرما» یا «توسط کارگزاری».
   - تغییرات اعلام‌شده کارفرما به‌صورت ساخت‌یافته: بیمه‌شده، نوع (شروع کار، ترک کار، تغییر حقوق)، تاریخ، منبع.
   - مراحل با تاریخ و ساعت کامل و کاربر انجام‌دهنده: درخواست تغییرات، دریافت تغییرات، تنظیم، تأیید، ارسال، پرداخت حق بیمه، اعلام حق‌الزحمه، تسویه.
   - تاریخچه هر تغییر وضعیت (منبع گزارش کارکرد پرسنل).
   - توضیحات آزاد.
   - هشدار مهلت قانونی (پایان ماه بعد).
   - لیست نهایی‌شده قفل می‌شود. تغییر فقط با مجوز و ذکر دلیل.

7. مالی و بانک
   - پرداخت حق بیمه متصل به لیست، با مبلغ، تاریخ، شماره مرجع، کارت و رسید. اگر کارگزاری پرداخت کند، بدهی کارفرما ثبت می‌شود.
   - صورت‌حساب حق‌الزحمه برای هر لیست. مبلغ هنگام صدور ثابت می‌شود.
   - واریزهای کارفرما با رسید، کارت مبدأ، حساب مقصد کارگزاری و شماره پیگیری یکتا (ثبت تکراری ممکن نیست).
   - یک واریز می‌تواند بین چند صورت‌حساب تقسیم شود. پیش‌پرداخت و پرداخت ناقص پشتیبانی می‌شود.
   - تطبیق با گردش حساب بانک (ورود فایل اکسل بانک). واریز پس از تطبیق «تأییدشده» می‌شود.
   - دفتر حساب هر کارفرما ویرایش‌نشدنی است. اصلاح فقط با سند برگشتی. مانده تجمعی خودکار محاسبه می‌شود.
   - مبالغ به ریال و عدد صحیح. واحد پول قابل تنظیم (به دلیل مصوبه حذف چهار صفر).

8. گاوصندوق اطلاعات حساس
   - شماره کارت، تاریخ انقضا، CVV2 و رمز سامانه تامین رمزنگاری‌شده در سطح فیلد.
   - کارت‌های نامحدود برای هر شخص یا کارگاه. نمایش عادی: 4 رقم آخر و نام بانک.
   - کلید رمزگشایی بیرون از پایگاه داده.
   - نمایش فقط یک رکورد در هر بار، با مجوز، ذکر دلیل و ثبت در لاگ.
   - سقف نمایش برای هر کاربر. عبور از سقف = قفل حساب + پیامک به مدیر.
   - این اطلاعات در هیچ خروجی گروهی، گزارش یا API بیرونی نمی‌آید.
   - رمز پویا ذخیره نمی‌شود.

9. گزارش‌گیری و جستجو
   - جستجو با کد ملی، شماره کارگاه، نام و غیره.
   - درآمد روزانه، ماهانه و بازه دلخواه: کارمزد تعلق‌گرفته و دریافت‌شده.
   - کارکرد پرسنل بر اساس کاربر و بازه زمانی (مثلاً عصر یک روز خاص).
   - آمار لیست‌ها: ارسال‌شده، ارسال‌نشده، در انتظار پرداخت، حضوری و غیرحضوری.
   - صورت‌حساب و بدهی یا طلب هر کارفرما. پرونده هر بیمه‌شده.
   - چاپ برای کارفرما: گواهی پرداخت حق بیمه (مثال: لیست ماه 2/1405 برای 12 بیمه‌شده) و صورت‌حساب حق‌الزحمه، با شماره سریال و QR.
   - خروجی اکسل و PDF. فقط از نماهای فقط‌خواندنی پایگاه داده می‌خواند.

10. اطلاعات پایه
   - فهرست‌های قابل تعریف بدون برنامه‌نویسی: انواع تلفن، نقش، وضعیت کارگاه، گروه کارگاه، بانک‌ها، شعب تامین، کدهای شغلی.
   - تعرفه حق‌الزحمه (بخش 7 همین سند).

11. ورود داده از اکسل و پشتیبان‌گیری
   - انتقال یک‌باره فایل اکسل فعلی با پیش‌نمایش، اعتبارسنجی و گزارش خطا.
   - رمزهای سامانه تامین که در اکسل به‌صورت متن آشکار هستند، هنگام انتقال مستقیم به گاوصندوق بروند.
   - پشتیبان‌گیری طبق بخش 5.

==================================================
7. تعرفه حق‌الزحمه (پویا)
==================================================
- یک تعرفه عمومی برای همه کارگاه‌ها. تعرفه اختصاصی برای هر کارگاه وجود ندارد.
- فرمول:
  حق‌الزحمه = (تعداد بیمه‌شده × مبلغ هر بیمه‌شده) + مبلغ هر لیست + مبلغ پرداخت حق بیمه + سایر هزینه‌ها + مبلغ گروه
- اجزا:
  - مبلغ هر بیمه‌شده: ضرب در تعداد بیمه‌شده.
  - مبلغ هر لیست: عدد ثابت برای کل کار.
  - مبلغ پرداخت حق بیمه: فقط اگر پرداخت توسط کارگزاری انجام شده باشد.
  - سایر هزینه‌ها: مبلغ دستی همان ماه.
  - مبلغ گروه: جزء جداگانه بر اساس گروه کارگاه. اگر کارگاه گروه ندارد، صفر. گروه هیچ جزء دیگری (مثل مبلغ هر بیمه‌شده) را تغییر نمی‌دهد.
- هر جزء، از جمله مبلغ هر گروه، تاریخ شروع و تاریخ پایان اعتبار دارد. تاریخ پایان خالی یعنی هنوز معتبر است. دوره‌های اعتبار یک جزء نباید هم‌پوشانی داشته باشند.
- مدیر می‌تواند اجزا و مبالغ را بدون برنامه‌نویسی تغییر دهد.
- مبلغ محاسبه‌شده روی صورت‌حساب ثابت می‌شود. تغییر تعرفه ماه‌های گذشته را عوض نمی‌کند.
- مانده = حق‌الزحمه منهای پرداختی، به‌صورت تجمعی در دفتر حساب.
- مقادیر فعلی در اکسل (برای مقدار اولیه):
  - هر بیمه‌شده: 100000 ریال
  - هر لیست: 1108370 ریال
  - پرداخت حق بیمه: 554185 ریال

==================================================
8. اصول پایگاه داده
==================================================
- مدل «شخص واحد» با جدول نقش‌ها.
- همه اطلاعات تکرارشونده نامحدود و در جدول فرزند.
- تاریخچه به‌جای بازنویسی: از تاریخ و تا تاریخ.
- حذف فیزیکی ممنوع. فقط غیرفعال‌سازی با ثبت در لاگ.
- قفل همزمانی (optimistic concurrency).
- اعتبارسنجی رقم کنترل کد ملی، شماره کارت (Luhn) و شبا.
- تاریخ‌ها در پایگاه داده استاندارد ذخیره و به شمسی نمایش داده شوند. سال و ماه لیست عدد باشد.
- یکسان‌سازی «ي/ی» و «ك/ک» برای جستجو.
- همه محاسبات مالی تست خودکار داشته باشند.
- جداول پیشنهادی: Person، ContactPoint، Address، Workshop، WorkshopGroup، WorkshopRole، ContractRow، Insured، Employment، InsuranceList، ListRow، ListChange، ListStatusHistory، PremiumPayment، TariffComponent، Invoice، Receipt، Allocation، LedgerEntry، BankStatementLine، BankCard، SecretItem، User، Role، Permission، Session، AuditLog، AccessLog، SecurityLog، Lookup.

==================================================
9. راستی‌آزمایی (بدون خواندن دستی کد)
==================================================
- عامل بازبین جدا که کد عامل اول را برای خطای امنیتی و منطقی بررسی کند.
- اسکنرهای خودکار امنیتی.
- تست‌های خودکار گسترده با قاعده‌ها. مثال: مانده هر کارفرما همیشه برابر جمع بدهکار منهای بستانکار است.
- تست حمله: آیا کاربر می‌تواند کارگاه دیگری را ببیند؟ آیا رمزی در لاگ ذخیره می‌شود؟
- تست بار با داده حجیم ساختگی.

==================================================
10. فازهای بعدی (خارج از فاز 1)
==================================================
- مرکز پیام: یک مرکز با اتصال جدا برای هر کانال. پنل پیامک، سیم‌کارت عادی از طریق گوشی اندرویدی و ربات بله: خودکار. واتساپ و ایتا: نیمه‌خودکار. سروش‌پلاس: پس از قرارداد.
- آرشیو یکپارچه همه پیام‌ها در همه کانال‌ها.
